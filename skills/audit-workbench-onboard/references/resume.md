# 续接

用户说「继续」「接着做」时，先看上下文。

- 上下文里有当前阶段：直接接着做，只在下一次写操作前重新读要操作的对象。例如停在发布前确认，
  发布前重新 `get_editor`，草稿或已发布版本变了就重新走清单。
- 上下文里没有（新会话，或对话被压缩丢了细节）：按下面从线上状态判断，不问用户做到了哪一步。

## 从线上状态判断阶段

依次查，命中第一条就从那个阶段继续。

| 线上状态 | 从哪里继续 |
|-|-|
| `get_editor` 里没有草稿，也没有已发布版本 | 阶段 1 |
| 有草稿，草稿里有轮次的 `enqueueViewUrl` 为空 | 阶段 2，请用户补这几轮的入队视图 |
| 有草稿，每轮入队视图都已填 | 阶段 3 |
| 没有草稿，有已发布版本；`get_workflows` 有轮次未同步、失败或需人工同步 | 阶段 4 |
| 工作流都已同步；`created_workflows` 显示有未启用或模版二未修补的 | 阶段 4 |
| 工作流都已启用；`list_auditors` 名单为空 | 阶段 5 |
| 名单不为空 | 阶段 5 的绑定检查，然后阶段 6 |

发布会删除草稿，所以「有草稿」说明还没发布，或者发布后又有人改了配置。第二种情况先说明草稿的
保存时间，问用户这次是接着发布，还是只处理工作流和审核员。

从阶段 2 及以后恢复时，阶段 1 的底表事实（`app_token`、`table_id`、字段列表）要重新取：
`parse_feishu` 用 `summary.feishu_table_url`。人才招聘协作者在发布前再确认一次，
`ensure_app_collaborator` 可以重复调用，已存在时返回 `present`。

## 告诉用户

用一句话说明判断依据和接下来做什么，例如：「配置已发布 v2，第二轮工作流同步失败，先处理工作流。」
不要把每一项查询结果都列出来。

## 不要做的事

不因为用户之前确认过就跳过这次的确认，不拿上下文里旧的 config 直接发布。
