# 续接

用户说「继续」「接着做」时，先看上下文。

- 上下文里有当前阶段：直接接着做，只在下一次写操作前重新读要操作的对象。例如停在发布前确认，
  发布前重新 `get_editor`，草稿或已发布版本变了就重新走清单。
- 上下文里没有（新会话，或对话被压缩丢了细节）：调用一次 `onboard_status(env, project_id)`，
  按它返回的 `stage` 继续，不问用户做到了哪一步。

## onboard_status 怎么判断

工具一次读取配置、工作流（含飞书上的启用和修补状态）、审核员名单和飞书绑定，按阶段顺序判断，
命中第一条就停：

| 线上状态 | stage |
|-|-|
| 没有草稿，也没有已发布版本 | 1 |
| 有草稿，有轮次的入队视图为空（`missing_views` 列出这几轮） | 2 |
| 有草稿，每轮入队视图都已填 | 3 |
| 已发布，有工作流未同步、失败或需人工同步 | 4 |
| 工作流都已同步，有未启用、模版二未修补或读不到飞书状态的 | 4 |
| 工作流都已启用，审核员名单为空 | 5 |
| 有审核员，但有人未绑定或绑定状态读不到（见 `binding`） | 5 |
| 有审核员，全部已绑定 | 6 |

发布会删除草稿，所以有草稿说明还没发布，或者发布后又有人改了配置。第二种情况
`draft_after_publish=true`，先说明草稿的保存时间，问用户这次是接着发布，还是只处理工作流和
审核员。

## 接着做之前

- 从阶段 2 及以后恢复时，阶段 1 的底表事实（`app_token`、`table_id`、字段列表）要重新取：
  `parse_feishu` 用 `summary.feishu_table_url`。
- 发布前再调用一次 `ensure_app_collaborator` 确认人才招聘协作者，已存在时返回 `present`。
- 停在阶段 4 时，按 `workflows` 里的缺口走工作流交接；停在阶段 5 的绑定检查时，再调用
  `check_auditor_binding` 拿到要展示的 `binding_markdown`。

## 告诉用户

用一句话说明，直接用返回的 `reason`，再说接下来做什么。例如：「已发布 v2，有工作流没有同步完成
或需要处理，先处理工作流。」不要把每一项查询结果都列出来。

## 不要做的事

不因为用户之前确认过就跳过这次的确认，不拿上下文里旧的 config 直接发布。
