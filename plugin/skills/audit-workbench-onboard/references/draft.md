# 阶段 2：保存草稿，分三步确认

阶段 2 先按 [alignment.md](alignment.md) 做完语义对齐，再调用一次 `suggest_draft` 保存草稿，
然后分三个子步骤请用户确认：

| 子步骤 | 确认什么 | 展示 |
|-|-|-|
| 2.1 | 展示的字段集合、展示位置、编辑权限 | `report_markdown` |
| 2.2 | 字段映射（审核状态、审核人、talent_id 等角色字段）和状态枚举映射 | `mapping_markdown` |
| 2.3 | 每一轮的入队条件（视图链接） | `views_markdown` |

一次只展示一个子步骤的内容，用户确认这一步后再展示下一步。不要把三段合在一条消息里，也不要
在 2.1 里提前问映射或视图链接。三段文本都原样展示，不改写、不总结。每段的最后一行都是管理端配置页
链接，展示后不要再在它下面追加内容。

## 生成并保存

`suggest_draft(env, project_id, table_url, workbench_type, alignment, limit=5)`。

工具按规则计票并组装草稿：字段过半数参考项目有对应才纳入；区域和权限取多数，打平取最近发布的
项目；布局取覆盖字段最多的参考项目；状态映射按对齐表与参考项目汇总。草稿结构与管理端保存时
一致，打开配置页就能回显。

- 项目没有草稿时直接保存，返回三段文本和 `page_url`。
- 项目已有草稿时只返回预览，`report_markdown` 里会写明「尚未保存」。展示 2.1 的内容，说明会
  覆盖现有草稿，得到确认后带 `confirm=true` 再调用一次；生产环境另传 `confirm_project_id`。
  覆盖保存后，从 2.1 重新开始确认。
- 生产环境第一次调用如果是因为已有草稿而停在预览，确认时同时补 `confirm_project_id`。

## 2.1 确认展示的字段

展示 `report_markdown`。它列出每轮推荐的字段，用色块区分展示位置、圆点区分编辑权限，结尾只问
字段集合要不要调整，最后一行是管理端配置页链接。

报告展示完就停下等用户回复，后面不追加任何内容，让配置页链接留在最后：不加「你需要定两件事」之类的待办或问题清单，
不复述报告，不提前说 2.2、2.3 要确认什么。唯一的例外见 [alignment.md](alignment.md)：轮次是按
参考项目推断的，在报告前加一句「轮次按参考项目推断，请确认」。

- 用户说没问题，进入 2.2。
- 用户要增减字段、改展示位置或权限，按 [改配置](../../audit-workbench-config/SKILL.md) 的「改」
  执行，改完把改动结果告诉用户，再进入 2.2。
- 用户说已经在配置页改好了，不用回读核对，直接进入 2.2；之后的写操作前照常重新读草稿。

## 2.2 确认字段映射和状态枚举映射

展示 `mapping_markdown`。它按轮次分开，每轮先列 🔴 没推荐出来、需要用户选的项，再列 🟡 系统
自动推荐出来但需要确认的项。

- `mappings_to_confirm=false` 时，所有映射都按名称一致或多数参考项目推荐，展示这段结论后直接
  进入 2.3，不等用户回复。
- 🔴 的项必须由用户给出选择。用户没选完就不进入 2.3，提醒还差哪几项。
- 用户确认 🟡 的推荐值，或给出修改，按「改配置」的「改」更新草稿后进入 2.3。
- 2.1 里用户改过角色字段时，`mapping_markdown` 里的对应项可能已经过时。展示时说明这几项以 2.1
  的改动为准。

## 2.3 给出每一轮的入队条件

展示 `views_markdown`，请用户给出每一轮的入队视图链接。

用户给出链接后调用 `set_enqueue_views(env, project_id, view_urls)`，`view_urls` 的 key 是轮次 ID
（`round-1`、`round-2`……），value 是视图链接。工具逐个解析，解析失败则不保存，把原因转述给用户。
保存成功后原样展示返回的 `views_markdown`：每轮的视图名称和筛选条件、还差哪几轮，最后是配置页
链接，请用户核对。

用户只给了一部分轮次时，只更新这些轮次，其余留空，`missing_views` 列出还差的轮次。任何一轮的入队视图为空时，
不进入阶段 3：发布时会因为视图链接解析失败而被拒绝，或发布后该轮不会入队。

## 处理用户的修改

不要用对齐表覆盖用户已经改过的内容。用户回到前面的子步骤要改东西时，按「改配置」的「改」更新
草稿，再从他改的那一步往后继续确认。
