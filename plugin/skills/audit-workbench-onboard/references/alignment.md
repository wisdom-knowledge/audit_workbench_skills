# 阶段 2 准备：语义对齐

这一步由你（Agent）完成判断，规则性的计票和组装由 `suggest_draft` 工具按脚本完成，不要自己写
匹配或打分脚本。

## 取参考项目

`get_reference_configs(env, project_id, workbench_type, limit=5)`。返回按发布时间倒序排列的
参考项目精简配置，每个项目每轮有字段（名称、类型、展示位置、权限）、角色字段名、状态选项映射，
以及按字段名表示的布局。参考项目与本项目同环境，BOE 参考 BOE，生产参考生产。

`count=0` 时停下，告诉用户没有同模版的已发布项目可供参考，不做推荐。

## 判断轮次数

优先看阶段 1 读到的字段分组。分组名本身常带轮次语义，例如「一轮审核」「二轮审核」，有 N 个
表示审核轮次的组，通常就是 N 轮。再结合底表里的审核状态列、审核员列名称（例如「一轮审核状态」
「二轮审核状态」）确认。

没有分组或分组看不出轮次时，按字段名称里的轮次标记判断；仍判断不出，取参考项目里最常见的轮数，
并在展示 2.1 报告前加一句「轮次按参考项目推断，请确认」，不另列其他待确认事项。轮数判断结果只作为对齐表的结构，不在
这一步写库。

参考项目轮数少于本项目判断出的轮数时，多出来的轮次对照参考项目的最后一轮；反之，本项目没有
的轮次不要出现在对齐表里。

## 对齐表结构

以**本项目底表的每个字段**为基准。不要先在参考项目之间聚类，只回答「这个新字段在参考项目 A
里对应哪个字段，或者没有对应」。

```json
{"rounds": [
  {"round": 1,
   "fields": [
     {"field_id": "fldA", "matches": {"1201": "题目ID", "1188": "题目ID", "1150": null}}
   ],
   "roles": {
     "status": {"field_id": "fldS", "basis": "exact", "reason": "名称与单选类型一致"},
     "talent_id": {"field_id": "fldT", "basis": "semantic", "reason": "参考项目叫「一轮审核员talent_id」"}
   },
   "status_mapping": {
     "待审核": {"target": "待审核", "basis": "exact", "reason": "文案一致"},
     "打回修改": {"target": "待返修", "basis": "semantic", "reason": "「打回」表示返修"}
   }}
]}
```

- `matches` 的 key 是参考项目 ID 字符串，value 是该项目**同一轮**里的字段名；没有对应写 null。
  只写参考项目里真实存在的字段名，写错的名字会被工具忽略、不算这一票。
- `fields` 只放阶段 1 `parse_feishu` 返回的本底表字段 ID。放进不存在的 ID 会被工具拒绝。
- `roles` 可选五个键：`status`、`reviewer`、`talent_id`、`audit_advice`、`audit_action`。
  模版二必须有 `audit_action`。判断时先按分组缩小候选，再在组内按名称、类型和选项判断。
  类型是硬约束：审核状态必须是单选，审核人通常必须是人员，talent_id 通常是文本或数字。
- `status_mapping` 的 key 是本项目审核状态字段的 `options` 文本，value 的 `target` 只能是平台
  七个状态之一：待审核、审核通过、审核拒绝、已返修待审核、待返修、其他、做题中。
- `basis` 只有三种：`exact` 名称或文案完全一致、类型也匹配；`semantic` 凭语义或分组推断；
  `none` 判断不出。拿不准一律写 `semantic`，不要为了好看写 `exact`。
- `reason` 一句话写清依据，它会进入给用户的报告。

## 判断缺项的处理

某个角色字段找不到时，把 `basis` 写 `none`、`field_id` 留空，不要拿一个不相干的字段顶替。
某个状态选项没有对应平台状态时同样写 `none`。工具会把这些列进 2.2 的 🔴 项，请用户选择。

## 完成后

把对齐表作为 `alignment` 传给 `suggest_draft`，按 [draft.md](draft.md) 分 2.1、2.2、2.3 三步
请用户确认。不要先把对齐表展示给用户看，报告由工具生成并原样展示。
