# 业务模型

## 对象

一个项目对应一张飞书底表。审核分若干轮，每轮在底表上有自己的审核状态、审核人、talent_id 等列。

- **配置**：每轮展示哪些字段、字段权限与区域、布局、角色字段映射、审核状态选项到平台状态的映射、
  入队视图。先存为草稿，发布后成为一个版本，发布时草稿被删除。
- **工作流**：发布后由后端 Worker 以「人才招聘」应用的身份在飞书上创建，每轮一条入队工作流；
  模版二每轮另有一条审核操作工作流。新建的工作流默认未启用。
- **任务**：平台侧每条记录每轮一行，分给本轮审核员。专家端按任务展示。
- **审核员**：项目审核员名单里的 talent_id。底表「审核人」列是飞书账号，两者靠审核员在专家端
  自行完成的飞书绑定对应起来。

配置是目标，工作流、审核员名单是按目标落到线上的结果。判断做到哪一步时，看线上结果和配置是否
一致，只补不一致的部分。

## 依赖链

一条记录要出现在审核员的专家端，必须依次满足下面每一环。排查时从前往后查，停在第一个不满足的
环节。每一环用它自己的证据下结论，不拿前一环的成功推断后一环。

| 环节 | 证据 |
|-|-|
| 配置已发布，项目未暂停 | 已发布版本号、运行状态 |
| 上一轮已通过（第 2 轮起） | 上一轮任务状态 |
| 记录满足该轮入队条件 | 飞书记录当前值，按发布时固化的视图筛选求值 |
| 该轮入队工作流已同步并启用 | 同步记录、飞书上的启用状态 |
| 工作流已调用入队并建出任务 | 任务记录 |
| 任务分给了这位审核员 | 任务上的审核员 talent_id，底表本轮 talent_id 单元格 |
| 审核员在项目名单中 | 审核员名单 |

`trace` 工具按这个顺序逐环检查一条记录。人才招聘是不是底表协作者不在里面，发布前由
`ensure_app_collaborator` 保证。

提交之后还有两环：结果回写飞书；通过后进入下一轮。下一轮同样要满足它自己的入队视图条件。

## 两个模版

模版类型是配置里的 `workbenchType`。

- **模版一**：审核员在专家端选审核状态并提交。平台把本轮可编辑字段和审核状态回写飞书；通过后
  按飞书上的实际状态和下一轮入队条件晋级。
- **模版二**：审核员点「打回 / 通过 / 拒绝」。平台把本轮可编辑字段和这个值写回飞书，值写在本轮
  「审核操作」列，不直接改审核状态。飞书上的
  审核操作工作流据此改审核状态，状态变化再经入队工作流同步回平台，晋级发生在这次同步之后。
  接口建不出「清空审核操作列」这一步，审核操作工作流发布后要人工在飞书上补，补完才能启用。

平台回写飞书会再次触发入队工作流。入队时如果平台上本轮已是终态（通过、拒绝等），这次调用被
忽略，不会来回写。
