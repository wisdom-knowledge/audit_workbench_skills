# 通用规则

所有子技能都按这份执行。工具全部来自 `audit-workbench` MCP，随插件安装，安装与更新见 [安装](install.md)。`audit-workbench-enqueue-workflow`
skill 不参与，也不要调用它的脚本。

## 写操作

1. 写操作默认只返回预览。把预览给用户看，用户同意后才带 `confirm=true` 再调用一次。
2. 生产环境（`env=prod`）的写操作还要传 `confirm_project_id`，值与 `project_id` 相同。
3. 两个例外可以直接写：项目没有草稿时的 `suggest_draft`；用户在对话里亲手给出的入队视图链接，
   用 `set_enqueue_views` 写入。用户给出的 talent_id 也视为已确认要添加，但 `add_auditors`
   仍然先预览，把会跳过的人说清楚再执行。
4. 已经确认过的内容，不因为对话里隔了几轮就当作仍然有效。真正执行前，重新读一次要操作的对象，
   和用户确认时看到的不一致就重新确认。

## 读状态

1. 同一会话里已经查过的结果直接用。只有要对某个对象做写操作前，才重新读这个对象。
2. 新会话，或者上下文里找不到当前进度时，接入流程用 `onboard_status` 从线上状态判断做到哪一步，
   不靠本地文件记录。
3. 线上状态和用户描述不一致时以线上为准，用一句话说明差异。

## 出错

1. 返回 `unauthorized` 时调用 `login(env)`，登录后重试刚才那一次调用。
2. 返回 `conflict` 时不强行覆盖。重新 `get_editor`，说明配置已被别人改过或发布过，请用户确认后
   再做。
3. 工具返回 `ok=false` 时把原因原样转述。同一个调用最多重试一次。
4. 底表缺列、权限不足、接口失败时停下，说明原因和下一步，不猜测补齐，不跳过步骤。

## 对用户说话

1. 说话要短，用户没问的不主动展开。
2. 工具返回的 `report_markdown`、`checklist_markdown`、`workflows_markdown`、
   `binding_markdown`、`setup_markdown` 原样展示，不改写，不总结，不补解释。
3. 只把真正调用过工具、拿到成功结果的事说成已完成。没查的写「未核验」，不推断成成功。
